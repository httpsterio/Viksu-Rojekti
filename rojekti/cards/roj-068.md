## Problem

Epic/tag/status rename detection in `save_board_config` (`commands.rs`) is index-based — it compares entries at the same position in the old and new arrays. Reordering or deleting any entry shifts indices, causing the backend to interpret the shift as a rename and propagate it to card files. Cards get assigned wrong epics/tags/statuses.

Cards intentionally store human-readable names (not IDs) to keep `.md` files readable without referring to `rojekti.config.yaml`. This must not change.

## Solution

Add a stable `id` field to each epic, tag, and status entry in `rojekti.config.yaml`. IDs are used only for rename detection in the backend — they never appear in card files. Cards continue to store names as strings.

```yaml
# rojekti.config.yaml
epics:
  - id: a3f9c1
    name: Board
    color: '#0062ff'
```

```yaml
# card frontmatter — unchanged
epic: Board
```

Rename detection changes from index-based to ID-based: find the old entry with matching ID, compare names, propagate rename to card files if different. Reorder and delete no longer produce false renames.

## ID generation

Use the `uuid` crate (v4) for ID generation. Add to `Cargo.toml`. Generate on the backend — no frontend involvement needed.

## Migration

Existing config entries have no IDs. On `read_board_config`, auto-assign a UUID v4 to any entry missing an ID and immediately write the config back. This is a one-time silent migration — no user action required.

## Changes required

**`Cargo.toml`**
- Add `uuid = { version = "1", features = ["v4"] }`

**`models.rs`**
- Add `id: String` to `Epic`, `Tag`, `Status` structs
- Use `#[serde(default)]` so old config files without IDs deserialise without error

**`storage.rs`**
- In `read_board_config`: after deserialising, check if any entry has an empty ID and assign a UUID v4 if so, then write the config back before returning
- Alternative: do the migration in a separate `ensure_ids` function called from `commands.rs`

**`commands.rs`** (`save_board_config`)
- Replace index-based rename detection with ID-based:
  - For each entry in the new config, find the entry in the old config with the same ID
  - If names differ → rename
  - If no matching ID in old config → new entry, no rename
  - If an old ID is absent from new config → deletion, no rename
- Remove the "position-stable" comment — the assumption no longer holds and the comment is misleading

**`init_project`**
- Assign UUID v4 IDs to all initial statuses, epics, tags, and priorities when creating a new board

**`src/types/index.ts`**
- Add `id?: string` to `Epic`, `Tag`, `Status` interfaces (optional for backward compat)

**`BoardSettingsModal.vue`**
- Ensure IDs are preserved when the user saves — they must not be stripped. The `_dragId` removal already scopes to that field only, so IDs should pass through, but verify.

## Rename batching (fix pre-existing swap bug)

Currently `save_board_config` calls `rename_epic_or_tag` in a loop, and each call immediately invokes `apply_pending_renames`. This means a swap ("Alpha" → "Beta", "Beta" → "Alpha") corrupts data: the first rename turns all Alpha cards into Beta, then the second rename turns all Beta cards (including the former Alphas) into Alpha.

Fix: set all `pending_rename` fields first, then call `apply_pending_renames` once after the loop. The rename propagation already handles multiple renames in a single pass correctly — only the call site needs to change.

## ID migration

Migration must happen at startup in `lib.rs`, in the setup hook **before the watcher is started**. This avoids triggering a spurious board reload — the watcher isn't running yet when the config is written.

Do not assign IDs inside `read_board_config`. Side-effect writes inside a read function are unexpected and will fire the watcher on every app load once the watcher is running.

## Notes

- Priorities do not participate in card frontmatter (cards reference priority by index number, not name) so they do not need IDs for rename detection. Adding IDs for consistency is optional.
- The WAL (`pending_rename`) system remains unchanged — it handles the actual propagation to card files. Only the detection that feeds into it changes.
- Do not add IDs to card frontmatter under any circumstances.
