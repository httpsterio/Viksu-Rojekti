## What this project actually needs protecting from

Rojekti stores everything as files. There is no database, no transaction log, no recovery mechanism. If a card gets silently corrupted — wrong field, dropped tag, mangled frontmatter — the user may not notice until much later, and there is no way to roll back. This shapes the entire testing philosophy: **the test suite exists to protect data integrity, not to verify UI behavior.**

Everything else is secondary.

## The two layers worth testing

**Backend (Rust) — high priority**

The Rust layer is where data actually moves. Cards are parsed, serialized, renamed, deleted, and written to disk here. The logic is stable, the functions are pure or near-pure, and the consequences of bugs are permanent. This is the right place to invest in tests first and keep them maintained over time.

The most important behaviors to pin down:
- Parsing and serialization are inverses of each other (round-trip integrity)
- Malformed or incomplete card files fail gracefully rather than panicking or silently dropping data
- The rename propagation system applies changes to all affected cards and leaves nothing in a half-renamed state
- ID generation never reuses or skips an ID (this applies to both card IDs via `nextId` and to the stable IDs for epics, tags, and statuses introduced in roj-068)
- Reordering config items does not trigger rename propagation — see below

**Frontend filter/sort logic (TypeScript) — low-to-medium priority**

The filtering and sorting in `useBoard.ts` is pure logic decoupled from Vue reactivity and from Tauri. It's cheap to test and does change with some regularity as new filter types are added. Worth a lightweight test file that runs against arrays of card fixtures — not because bugs here are catastrophic, but because regressions are easy to introduce and easy to catch.

## What is not worth testing right now

**Vue components** — too tightly coupled to the UI and too likely to change. Any test written today would need rewriting next week. The cost of maintaining them exceeds the value.

**Tauri commands** — these are thin wrappers that delegate immediately to `storage.rs`. Testing them requires the full binary and the IPC layer. If `storage.rs` is tested, `commands.rs` is covered by implication.

**The index file** — it is derived state, always rebuildable from the card files. Testing that it stays in sync is lower value than testing that the card files themselves are correct.

**Drag and drop / positioning** — the most WIP part of the codebase. The logic will change. Leave it alone for now.

## The rename regression test (high priority)

The rename propagation system was previously index-based: `save_board_config` identified renames by comparing entries at matching positions. This caused a critical bug — reordering epics in settings would silently reassign cards to the wrong epic, because the entry at index 0 after reorder had a different name than the entry at index 0 before.

The fix (roj-068) made rename detection ID-based: each `Epic`, `Tag`, and `Status` now has a stable UUID in `rojekti.config.yaml`. Renames are detected by matching on `id` and comparing names. Reordering entries changes positions but not IDs, so no rename is detected.

The regression test to write: construct a `BoardConfig` where two epics are present, submit a new config with those same epics reordered (names and IDs unchanged, just swapped positions), and assert that `apply_pending_renames` is never called — i.e., no card files are rewritten and no `pending_rename` fields are set.

This test encodes the exact failure mode that was missed and would not have been caught by any upfront test design. It should be written before implementing the test suite to serve as the anchor case.

## The right time to add a test

Not everything needs a test from day one. A good trigger: if you fix a bug and think "I can't believe that was broken," write a test before moving on. Regression tests written right after a bug is found are the most valuable ones — they encode exactly the case that was missed and would never have been thought of upfront.

## Summary

Write backend tests first, start with parsing. Keep frontend tests minimal and focused on filter logic. Ignore the UI layer entirely for now. As the data model stabilizes, the right test surface will become obvious on its own.
